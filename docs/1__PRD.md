## 2. Product Overview & Vision

Indian Railways (IR) operates one of the most saturated rail networks globally, where high-density passenger traffic and continuous freight corridors share identical track infrastructure. Infrastructure health is sustained by three independent technical departments:

- **Civil Engineering (Permanent Way / Track):** Monitored via the Track Management System (TMS).
- **Electrical Traction Distribution (TRD / OHE):** Monitored via the Traction Distribution Management System (TDMS).
- **Signal & Telecommunication (S&T):** Monitored via the Signal Maintenance Management System (SMMS).

Historically, maintenance demands are submitted independently into the Block Demand Management System (BDMS) without inter-departmental temporal or spatial synchronization. This decentralized approach forces Divisional Control Offices (using the Control Office Application - COA) to grant isolated, piecemeal line closures. This results in multiple speed restrictions, under-utilized track machine fleets, severe freight detention, and passenger delays.

**RAIL-BLOC Vision:** To deliver an AI-powered, mathematically bounded block scheduling optimization platform that automates multi-horizon maintenance planning (Strategic 26-Week Rolling Calendar, Tactical Weekly Plan, and Real-Time Operational Horizon). RAIL-BLOC unifies Civil, Traction, and Signal maintenance demands into synchronized "shadow blocks," maximizes asset uptime, minimizes train detention, and enforces the Indian Railways General and Subsidiary Rules (G&SR). **"Mathematically bounded" is a claim about constraint satisfaction, which is fully verifiable; it is not a claim of guaranteed global optimality under a hard solve-time budget (see TechSpec.md ADR-002).**

## 5. Non-Functional Requirements (NFRs)

- **NFR-001 (Optimization Latency):** The CP-SAT solver must produce a constraint-verified weekly divisional block schedule across 1,000+ track kilometers within $\le 35$ **seconds (p95)**. This is the single authoritative latency figure for routine solves — any other figure elsewhere in this document set (e.g., an earlier "≤30 seconds" figure in Tracker.md) is superseded by this NFR (DOC-002 fix).
- **NFR-002 (Emergency Re-planning Latency):** Localized real-time re-optimization during P0 line fractures must execute within $\le 45$ seconds, **inclusive of Sentinel's synchronous structural re-check** — this NFR does not authorize skipping Sentinel verification (see NFR-003, and TechSpec.md ADR-006).
- **NFR-003 (Safety Invariant Integrity):** 100% of generated block plans — routine and emergency — must pass deterministic Sentinel G&SR/MILP validation, bound to their exact `content_hash`, before being presented to human operators.
- **NFR-004 (System Availability):** High-availability architecture **targeting** 99.95% operational uptime for the backend API and database tiers. **This is a production target; it is not validated within the 5-day single-instance Docker Compose prototype build and must not be presented as a measured or achieved figure at this stage (DOC-006 / XC-009 fix).**
- **NFR-005 (Audit Immutability):** All block requests, approvals, overrides, and completions must be sealed in an append-only, advisory-locked, SHA-256 hash-chained relational table, enforced via an INSERT-only database role and `BEFORE UPDATE/DELETE` guard triggers — not solely by a `REVOKE` grant (DB-001 fix). The resulting ledger is **tamper-evident**, not tamper-proof.
- **NFR-006 (UI Rendering Performance):** The time-distance string chart and MapLibre GIS map **target** 60 FPS rendering performance with over 10,000 active vector entities. **This figure must be measured via FPS profiling on the actual demo scenario before being claimed as achieved (PERF-003 fix); until measured, the honest claim is "smooth pan/zoom on the demo scenario."**
- **NFR-007 (NEW — Approval Binding):** Every plan reaching `TRANSMITTED_COA` must carry a `content_hash` identical to the `sentinel_hash` recorded at its most recent `SENTINEL_PASSED` transition; any mismatch blocks the transition server-side (SAFE-002).
- **NFR-008 (NEW — Distinct Approver Integrity):** No single authenticated actor may occupy both the `decided_by` (Sr. DOM) and `authorized_by` (DRM) roles on the same plan; this is enforced by a database CHECK constraint, not merely a UI convention (APP-001).
